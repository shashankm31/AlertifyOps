# Database Architecture

## Overview

The database layer is responsible for storing, retrieving, updating, and deleting application data.

AlertifyOps uses SQLAlchemy ORM to communicate with the database instead of writing raw SQL queries.

During development, SQLite is used because it is lightweight and requires minimal configuration.

The application will later migrate to PostgreSQL for production deployment.

---

# Why Do We Need a Database?

A backend application must persist data.

Without a database, all information would be lost whenever the application restarts.

Example

Incoming Alert

Device : RTR-01

Status : DOWN

↓

Store inside Database

↓

Retrieve later

↓

Update if resolved

↓

Delete if no longer required

The database provides permanent storage for application data.

---

# Why SQLite?

SQLite was selected during the initial development phase because:

- No installation required
- Single database file
- Lightweight
- Easy to configure
- Suitable for local development

# Database Architecture

FastAPI

↓

SQLAlchemy ORM

↓

Database Engine

↓

SQLite Database

FastAPI never communicates directly with SQLite.

SQLAlchemy acts as an Object Relational Mapper (ORM) between the application and the database.

---

# database.py

The database.py module is responsible for configuring the database connection.

Current Responsibilities

- Create database engine
- Create database sessions
- Define Base class
- Provide database sessions to API routes

---

# Database Engine

Engine is responsible for establishing communication between the application and the database.

Current implementation

create_engine()

Responsibilities

- Connect to SQLite
- Execute SQL generated by SQLAlchemy
- Manage database connections

Think of the Engine as the bridge between FastAPI and the database.

---

# SessionLocal

SessionLocal creates database sessions.

A session represents one conversation between the application and the database.

Every database operation uses a session.

Examples

Insert

Read

Update

Delete

All CRUD operations are executed using SessionLocal.

---

# Why Sessions?

Instead of opening one permanent database connection for the entire application, FastAPI creates a new session for every request.

Request

↓

Create Session

↓

Perform CRUD

↓

Close Session

This improves reliability and resource management.

---

# Base

Base is the parent class for all SQLAlchemy models.

Current Model

Alert

inherits from

Base

Every model that represents a database table must inherit from Base.

Example

class Alert(Base)

Without Base, SQLAlchemy cannot recognize the model as a database table.

---

# declarative_base()

Base is created using

declarative_base()

Purpose

Create a common parent class for all database models.

Every SQLAlchemy model inherits from this base class.

---

# get_db()

The get_db() function provides a database session to API routes.

Responsibilities

- Create Session
- Yield Session
- Close Session automatically

This prevents unused database connections from remaining open.

---

# Dependency Injection

API routes receive database sessions using

Depends(get_db)

Example

db: Session = Depends(get_db)

FastAPI automatically calls get_db() and injects the session into the API.

This avoids manually creating and closing sessions inside every endpoint.

---

# SQLAlchemy ORM

SQLAlchemy converts Python objects into SQL queries.

Instead of writing

INSERT INTO alerts ...

the application writes

db.add(alert)

SQLAlchemy generates the SQL automatically.

Benefits

- Cleaner code
- Database independent
- Easier maintenance
- Object-oriented programming
